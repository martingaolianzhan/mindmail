# MindMail Stabilisation Plan

**Single source of truth.** Consolidated from the supplied Existing Bug List and the local Baseline Diagnostic Report. Scope is stabilisation only: removed Neon projects and real Aurinko mailbox connections must never be accessed, recreated, probed, or synchronised without explicit later authorisation.

## Rules and status

- **Status:** `TODO` = not started; `IN PROGRESS` = active change; `BLOCKED` = cannot proceed safely; `DONE` = acceptance criteria verified by the stated tests or explicit recorded manual verification.
- A successful typecheck, lint, or build alone never changes an item to `DONE`.
- Use npm and **Vitest**. Automated tests must never contact real Neon, Clerk, Aurinko, Gmail, or Gemini services. Use mocked services/synthetic fixtures for unit tests and only a disposable local PostgreSQL database for integration tests.
- No migration, `db push`, OAuth exchange, mailbox sync/send, or live AI request is permitted unless separately authorised.
- Priority: P0 blocks safe use; P1 blocks dependable demo/public readiness; P2 quality/documentation; P3 polish. Dependencies are plan IDs; `—` means none.

### SYNC-007 follow-up — resource exhaustion and retry consequences

The configured limits and measurement definition remain those recorded in the resource-limit close-out above; no second limit inventory is introduced here. Exceeding a page, record, single-response or cumulative-response limit ends the run safely: the knowingly incomplete dataset is not successful sync, and that run does not advance the durable final delta checkpoint. If the same Account generation remains authoritative, no other authoritative sync completes and no relink or other ownership/checkpoint transition occurs in the meantime, a later retry begins from the still-unadvanced trusted checkpoint. This is conditional, not a promise that every later run always starts from exactly the same checkpoint; SYNC-004/SYNC-006 authority and reinitialization rules still apply.

If the underlying provider change set consistently exceeds the configured per-run limits, retrying from the same trusted checkpoint may repeatedly hit the same safety limit. **SYNC-005 scheduling/retry does not by itself make a deterministically oversized change set completable.** Its existing durable scheduling/recovery/retry responsibilities are unchanged.

The cumulative mailbox-payload limit remains a practical serialized-payload/workset safety proxy, not an exact Node/V8 heap-memory ceiling. Parsed JavaScript objects, temporary serialization and Axios/Node runtime allocations can make actual peak heap usage larger. This clarification does not create a memory-engineering task or reopen completed SYNC-007.

### Future design option — bounded batching / streaming persistence

If explicitly authorised real-service validation shows that normal supported mailbox workloads regularly exceed safe in-memory accumulation bounds, investigate bounded batching or streaming persistence rather than simply removing resource limits. **This direction is preserved as a future option only**, not a current implementation requirement or a new backlog task. Only INT-002 evidence should decide whether to promote it into a separately scoped implementation task.

A possible design would:

- Consume provider pages or bounded batches incrementally and persist completed pages/batches without retaining the entire provider change set in memory.
- Preserve idempotent, retry-safe/convergent persistence, authoritative SyncExecution writes, SYNC-004 generation/run fencing, and stale-run/relink protection.
- Allow successfully persisted child records/batches to remain when a later page/batch fails, where existing idempotent convergence semantics permit. Keep the final provider delta checkpoint unadvanced so a later retry from the still-trusted checkpoint can safely reprocess those records; whole-run rollback is not required. This does not change current SYNC-002/SYNC-004 semantics.
- Keep the durable final provider delta checkpoint unchanged until the complete authoritative provider change set for that run has been successfully processed. Partial batch persistence is never permission to advance that final checkpoint.
- Retain finite page/record/byte/deadline controls, and evaluate increased database operations, relink races, fencing checks and run-deadline costs before implementation.

Bounded batching/streaming may reduce retained in-memory mailbox data, but **by itself does not make a provider change set exceeding the per-run page limit or overall run deadline completable**. A change set still requiring more pages than the configured maximum will still reach that limit, fail safely and leave the final delta checkpoint unchanged even if earlier pages were persisted. Normal supported workloads exceeding page/deadline bounds require INT-002 evidence and verified provider semantics to decide between still-finite limit adjustments and a provider-supported segmented continuation/recovery strategy; streaming alone is not the answer. 

Streaming reduces peak retained mailbox data, but it does not reduce the total serialized response bytes fetched during a run. If the same change set exceeds the current 128 MiB cumulative per-run budget, streaming under that unchanged budget will still fail safely. Any future batching/streaming design must use INT-002 evidence to decide how to redefine or tune that still-finite total-work limit while separately bounding data retained in memory; it must preserve the terminal-checkpoint and fencing rules above.

An intermediate `nextPageToken` / `pageToken` is pagination state only. It must not be promoted into a durable recovery checkpoint unless future provider documentation explicitly proves such a contract. The existing boundary remains: **only the terminal provider delta checkpoint may become the durable sync checkpoint after the complete authoritative change set has been processed successfully**.

Ownership distinction remains unchanged: SYNC-007/INT-002 resource limits concern how much work one run can safely process; potential future batching/streaming concerns retained memory and bounded persistence structure; SYNC-009 owns complete recovery of historical mailbox activity outside the supported initial/recovery window. Larger page/byte limits, batching, streaming, SYNC-005 scheduling and provider retries do not by themselves solve SYNC-009 historical completeness.
